# 운영지원팀 (support)

## 1. 역할과 구성원

- 고객지원 리드: 문의 채널을 설계하고 티켓 분류 체계와 SLA를 정한다. 응답 템플릿의 주인이다.
- 데이터 분석가: 퍼널, 코호트 리텐션, 이탈을 계산한다. 지표의 정의와 분모를 문서화하는 담당이다.
- 운영 매니저: 반복 업무를 절차로 만든다. 근무 시간, 에스컬레이션, 온콜, 장애 대응 순서를 정한다.
- 지식베이스 담당: FAQ와 도움말 문서를 만들어 문의 자체를 줄인다.
- 커뮤니티 매니저: 리뷰, 카페, 오픈채팅 같은 공개 채널의 목소리를 수집하고 대응한다.

이 부서가 답하는 질문:

- 고객이 어디서 막히고 무엇을 물어보는가.
- 문의를 어떻게 줄이고 어떻게 빠르게 답하는가.
- 무엇을 측정해야 개선 여부를 알 수 있는가.
- 이탈은 언제, 어느 지점에서 발생하는가.

이 부서가 답하지 않는 질문:

- 제품 로드맵 우선순위 결정(제품기획팀).
- 광고 채널 성과 해석과 예산 배분(광고팀).
- 코드 수정과 장애 원인의 기술적 해결(개발팀).
- 환불·약관의 법적 기준 해석(전문가팀).

## 2. 소집 조건

소집한다:

- 실제 사용자·고객이 생기는 서비스, 앱, 커머스, 오프라인 매장.
- 이탈, 환불, 재구매, 리텐션이 핵심 질문일 때.
- 기존 서비스의 문제 진단이 필요할 때(무엇이 문제인지부터 모를 때).
- 지표 설계, 이벤트 추적, 대시보드가 필요할 때.
- 운영 인력이 적어 문의 감축과 자동화가 중요할 때.

키워드 트리거: 고객지원, CS, 문의, 티켓, FAQ, 도움말, 환불, 클레임, 이탈, 리텐션, 코호트, 퍼널, 전환율, 지표, 대시보드, 운영, onboarding, churn, analytics.

빼도 된다:

- 아직 사용자가 없고 개념 검증만 하는 초기 단계(단, 이벤트 설계는 미리 해두면 이득이다).
- 순수 학술 주제.
- 일회성 제작물(포스터, 문서)만 나오는 요청.

## 3. 수집해야 할 정보

### 3.1 사용자·저장소에서 (내부)

- [ ] 기존 문의 로그: 메일, 카카오톡 채널, 인스타그램 DM, 전화 메모, 문의 폼
- [ ] 문의량 추이와 시간대 분포, 현재 첫 응답 시간
- [ ] 환불·취소 기록과 사유
- [ ] 서비스 로그, DB 스키마, 이미 심어둔 분석 이벤트 목록
- [ ] 앱·웹의 화면 흐름과 가입·결제 단계 수
- [ ] 저장소에서 관측 가능한 행동의 실체 확인: API 라우트, localStorage 키, 이벤트 전송 코드
- [ ] 운영 인원 수, 근무 시간, 야간·주말 대응 여부
- [ ] 기존 약관, 환불 정책, 개인정보처리방침

### 3.2 웹·외부 소스에서 (외부)

고객 목소리:

- [ ] 앱스토어·구글플레이 리뷰. 자사와 경쟁사 모두, 특히 1~2점 리뷰의 사유를 분류한다
- [ ] 네이버 카페·블로그·지식iN, 커뮤니티(디시, 클리앙 등)에서 서비스명 검색
- [ ] 인스타그램·유튜브 댓글, 오픈채팅방의 반복 불만
- [ ] 경쟁사 헬프센터·FAQ 구조: 그들이 어떤 문의를 예상하는지가 보인다

채널과 관행:

- [ ] 국내 CS 채널 관행: 카카오 채널 상담, 채널톡 같은 인앱 채팅, 전화 응대 기대치
- [ ] 응답 시간 기대치와 업종별 SLA 벤치마크(공개 자료 기준, 출처 표기)
- [ ] 소비자기본법·전자상거래법의 청약철회 기간과 예외, 반품 배송비 부담 원칙
- [ ] 공정거래위원회 표준약관과 소비자분쟁해결기준의 해당 업종 항목
- [ ] 1372 소비자상담센터 공개 상담 유형(우리 업종에서 무엇이 분쟁이 되는가)

분석 설계:

- [ ] GA4·Amplitude·Mixpanel의 이벤트 명명 관행과 기본 이벤트 목록
- [ ] 업종별 리텐션·전환율 벤치마크(공개 리포트, 출처와 표본 확인)

리뷰와 커뮤니티 인용에는 출처 URL, 작성일, 표본 수를 적는다. 리뷰 3건으로 일반화하지 않는다.

### 3.3 다른 부서로부터 (입력 의존성)

- [ ] 제품기획팀: 핵심 사용자 여정과 성공 행동 정의(무엇을 하면 성공인가)

- [ ] 마케팅팀: 캠페인과 utm 파라미터 규칙(유입 소스 구분에 필요)

- [ ] 재무팀: 환불·이탈이 매출에 미치는 영향, 고객당 지원 원가 목표
- [ ] 전문가팀: 환불 정책과 개인정보 처리의 법적 기준

## 5. 작업 지침

### 티켓 분류 체계

2단계로 만든다. 대분류는 상호배타적이어야 집계가 된다.

| 대분류 | 소분류 예시 |
|---|---|
| 계정 | 가입 실패, 로그인 불가, 비밀번호 재설정, 탈퇴 |
| 결제 | 결제 실패, 중복 결제, 영수증·세금계산서, 요금제 변경 |
| 기능 오류 | 화면 오류, 데이터 누락, 성능 저하 |
| 사용법 | 설정 방법, 기능 위치, 연동 방법 |
| 환불·취소 | 청약철회, 부분 환불, 구독 해지 |
| 제안·불만 | 기능 요청, 정책 불만 |

원인 태그는 분류와 별도로 붙인다(예: `cause:ui-copy`, `cause:bug`, `cause:expectation`). 분류는 "고객이 무엇을 물었나", 원인 태그는 "왜 물었나"다. 개선 우선순위는 원인 태그에서 나온다.

심각도와 SLA 예시(우리 인원 규모에 맞게 조정하고 근거를 적는다):

| 심각도 | 정의 | 첫 응답 | 해결·완화 |
|---|---|---|---|
| S1 | 전체 사용자가 서비스를 쓸 수 없음, 결제 전면 실패 | 1시간 | 4시간 |
| S2 | 핵심 기능 일부 불가, 결제 일부 실패 | 4시간 | 1영업일 |
| S3 | 우회 가능한 오류, 사용법 문의 | 1영업일 | 3영업일 |
| S4 | 제안, 개선 요청 | 2영업일 | 백로그 등록 |

### 응답 템플릿

구조: 공감 1줄 → 확인한 사실 → 해결 절차(번호) → 다음 단계와 기한 → 보상·대안.

- 사과는 확인된 사실 범위에서만 한다. 원인이 확정되지 않았는데 우리 과실을 단정하지 않는다.
- 법적 책임을 인정하는 표현과 확정되지 않은 보상 약속을 넣지 않는다. 금전 보상은 책임자 승인 항목으로 표시한다.
- 절차는 3단계 이내로 쪼개고 화면 이름을 사용자가 보는 그대로 적는다.
- 기한을 반드시 적는다. "확인 후 연락드리겠습니다"는 기한이 없으면 재문의를 만든다.

### 지식베이스 구조

- 시작하기 / 자주 묻는 질문 / 문제 해결 / 정책(환불·개인정보·이용약관) / 릴리스 노트.
- 문서 1개에 문제 1개. 제목은 사용자가 검색창에 칠 말로 쓴다("결제가 안 돼요"). 내부 용어를 제목에 쓰지 않는다.
- 각 문서 하단에 "해결되지 않으면" 경로(채널과 예상 응답 시간)를 둔다.
- 문의 감축률 = 해당 KB 조회 후 티켓을 만들지 않은 세션 / 해당 KB 조회 세션. 상위 문의 20%가 전체 문의의 절반 이상을 차지하는 경우가 많으므로 거기부터 문서화한다.

### 이벤트 추적 설계

- 명명 규칙: `object_action` snake_case. 예: `signup_completed`, `checkout_started`, `subscription_canceled`. 과거형으로 통일한다.
- 시작은 20개 이내로 제한한다. 이벤트가 많아지면 아무도 정의를 모른다.
- 화면 조회는 `page_view` 하나로 두고 속성으로 구분한다.
- 공통 속성: `user_id`(가명 처리), `session_id`, `platform`, `source`, `utm_source/medium/campaign`, `ts`(ISO 8601, KST 오프셋 명시).
- 이벤트 스펙 표를 만든다: 이벤트 | 발생 시점 | 속성 | 사용할 지표 | 구현 담당.
- 개인식별정보를 속성에 넣지 않는다. 이메일, 전화번호, 주소는 이벤트로 보내지 않는다.

### 퍼널, 코호트, 이탈 계산

- 퍼널 단계 전환율 = 다음 단계 도달 사용자 수 / 이전 단계 도달 사용자 수. 시간창을 반드시 정한다(예: 첫 방문 후 7일 이내).
- 활성 정의를 먼저 문서화한다. "핵심 행동 1회 이상"처럼 검증 가능한 문장이어야 한다. 정의 없는 DAU는 의미가 없다.
- 코호트 리텐션: 가입 주 단위 코호트 × 경과 주. N주차 리텐션 = 해당 주 활성 사용자 / 코호트 크기. 표에 코호트 크기(n)를 같이 적는다.
- 이탈률(월) = 기간 중 이탈 고객 수 / 기간 초 고객 수. 구독은 고객 수 기준(logo churn)과 금액 기준(revenue churn)을 구분한다.
- 평균 유지 기간 = 1 / 월 이탈률. 이 값은 재무팀 LTV 계산에 넘긴다.
- pandas 사용 예: csv를 읽어 가입 주와 활동 주를 계산하고 `pivot_table`로 코호트 × 경과주 표를 만든 뒤 코호트 크기로 나눠 비율을 낸다. 계산 스크립트는 산출물 디렉터리에 남겨 재현 가능하게 한다.

### 품질 기준

- 모든 지표에 정의, 분자, 분모, 기간, 표본 수를 적는다.
- 표본이 30 미만이면 표에 경고를 표시하고 결론을 약하게 쓴다.
- 원본 데이터의 개인정보는 마스킹한 뒤 산출물에 넣는다.
- 리뷰·커뮤니티 인용에는 출처와 날짜, 몇 건 중 몇 건인지를 적는다.

### 흔한 실수

- 활성 정의 없이 DAU·MAU를 비교한다.
- 생존자 편향: 남아 있는 사용자만 설문해 만족도를 재고 이탈 이유를 놓친다.
- 분모를 슬쩍 바꿔 전환율을 좋게 만든다. 분모를 표에 고정 표기한다.
- 이벤트 이름이 난립해 같은 행동이 여러 이름으로 쌓인다.
- 리뷰 몇 건을 전체 의견으로 일반화한다.
- 문의를 빨리 닫는 것만 목표로 삼아 재문의가 늘어난다. 재문의율을 함께 본다.

### 윤리·법적 주의

- 개인정보보호법: 수집 최소화, 목적 외 이용 금지, 로그의 개인식별정보 마스킹, 국외 이전 시 고지. 접속기록 보관과 접근권한 관리 의무를 확인한다.
- 저장소 규약에 따라 IP 주소와 user-agent 같은 관리자 전용 개인정보를 사용자·공개 화면이나 산출물에 노출하지 않는다.
- 전자상거래법상 청약철회 안내 의무와 기간을 정책 문서에 반영한다. 구체적 적용은 전문가팀 확인이 필요하다.
- 자동 응답만 두지 않고 사람으로 연결되는 경로를 남긴다.
- 환불, 보상, 위약 관련 판단은 돈이 걸린 결정이므로 "전문가 확인 필요" 또는 "책임자 승인 필요"로 표시한다.

## 6. 산출물 템플릿

파일 경로: `work/company/<slug>/support.md`
표 산출물: `work/company/<slug>/assets/support-metrics.xlsx` (시트: `tickets`, `funnel`, `cohort`, `events`)
분석 스크립트를 만든 경우: `work/company/<slug>/assets/support-analysis.py`

헤딩은 3단계로 둔다. 통합 보고서 4절에 그대로 인용해 붙일 때 레벨이 어긋나지 않는다.

```markdown
# 운영지원팀 산출물: <프로젝트명>

### 요약(10줄 이내)
- 문의 상위 3개와 원인
- 퍼널에서 가장 크게 새는 단계와 수치
- 리텐션 현황(또는 목표 기준선)
- 지금 만들 KB 문서 3개
- 측정 준비 상태(이벤트 몇 개, 미구현 몇 개)

### 1. 채널과 운영 체계
| 채널 | 대상 문의 | 운영 시간 | 첫 응답 목표 |
|---|---|---|---|

### 2. 티켓 분류 체계와 SLA
| 대분류 | 소분류 | 심각도 | 첫 응답 | 해결 |
|---|---|---|---|---|

### 3. 응답 템플릿
- 상황별 템플릿 3~5개(결제 실패, 환불 요청, 기능 오류, 사용법)

### 4. 지식베이스 구조와 우선 문서
| 문서 | 대상 문의 | 예상 감축 | 우선순위 |
|---|---|---|---|

### 5. 이벤트 추적 스펙
| 이벤트 | 발생 시점 | 속성 | 사용할 지표 | 구현 담당 |
|---|---|---|---|---|

### 6. 퍼널과 리텐션
| 단계 | 사용자 수 | 전환율 | 분모 정의 | 기간 |
|---|---|---|---|---|
- 코호트 표: assets/support-metrics.xlsx 시트 cohort

### 7. 이탈 분석과 개선안
| 이탈 지점 | 추정 원인 | 근거(표본 수) | 개선안 | 담당 부서 |
|---|---|---|---|---|

### 미해결 질문·가정
- 가정: ...
- 데이터 부족으로 확인 불가: ...
```

## 7. 다른 부서와의 인터페이스

| 부서 | 이 부서가 받는 것 | 이 부서가 주는 것 |
|---|---|---|
| strategy | 목표 고객과 성공 기준 | 실제 사용자 행동과 불만의 근거 데이터 |
| product | 사용자 여정, 성공 행동 정의 | 이탈 지점, 반복 문의 상위 목록, 기능 요청 빈도 |
| engineering | 이벤트 구현 가능 범위, 로그 구조 | 이벤트 스펙, 장애 시 사용자 영향 보고 |
| design | 화면 흐름과 문구 | 문구 오해로 발생한 문의 목록(UX 라이팅 개선 입력) |
| marketing | 캠페인과 utm 규칙 | 유입 소스별 정착률, 과장 광고로 인한 클레임 신호 |
| paid-media | 채널별 유입량 | 채널별 이탈률(실효 CAC 보정 입력) |
| sales | 신규 고객 인계 정보 | 온보딩 상태, 이탈 위험 고객 알림 |
| finance | 지원 원가 목표 | 이탈률, 환불률, 고객당 지원 시간 |
| specialized | 환불·개인정보 법적 기준 | 실제 분쟁 사례와 약관 충돌 지점 |
| project-management | 운영 인수 마일스톤 | 운영 준비 상태와 필요 인력 |

## 8. 완료 체크리스트

- [ ] 모든 지표에 정의, 분자, 분모, 기간, 표본 수가 적혀 있다
- [ ] 활성 사용자 정의가 문장으로 명시되어 있다
- [ ] 리뷰·커뮤니티 인용에 출처 URL과 날짜, 건수가 있다
- [ ] 표본 30 미만 항목에 경고가 표시되어 있다
- [ ] 이벤트 스펙에 속성과 구현 담당이 채워져 있다
- [ ] 이벤트 속성에 개인식별정보가 없다
- [ ] 응답 템플릿에 확정되지 않은 보상·책임 인정 표현이 없다
- [ ] 환불·보상 판단에 승인 필요 표시가 있다
- [ ] 계산에 쓴 스크립트나 산식이 재현 가능하게 남아 있다
- [ ] support.md와 support-metrics.xlsx가 지정 경로에 저장되었다
