# PM팀 (project-management)

## 1. 역할과 구성원

- 프로젝트 매니저: 범위를 정의하고 산출물 단위로 쪼갠다. 범위 변경 요청을 기록하고 일정·비용 영향을 계산한다.
- 일정 관리자: 의존성을 연결해 크리티컬 패스를 찾고, 버퍼를 어디에 둘지 정한다.
- 리스크 매니저: 리스크 레지스터를 운영한다. 확률과 영향을 점수화하고 완화 조치의 담당과 기한을 붙인다.
- 리소스 매니저: 부서별 가용 시간과 실효 가동률을 반영해 과부하 구간을 찾는다.
- 릴리스·QA 코디네이터: 릴리스 게이트(테스트 통과, 검수, 배포 승인)를 정의하고 통제한다.

이 부서가 답하는 질문:

- 무엇을 언제까지 누가 하는가.
- 무엇이 먼저 끝나야 다음이 시작되는가, 어디가 병목인가.
- 일정이 밀리면 어디가 먼저 무너지는가.
- 어떤 리스크가 가장 크고 무엇을 지금 준비해야 하는가.

이 부서가 답하지 않는 질문:

- 무엇을 만들지(제품기획팀), 어떻게 만들지(개발팀).
- 예산과 수익성(재무팀). 단 공수와 기간은 재무팀에 입력으로 준다.
- 계약·법적 기한의 해석(전문가팀).

## 2. 소집 조건

소집한다:

- 부서가 3개 이상 참여해 산출물이 여러 개 나오는 프로젝트.
- 출시일, 공모 마감, 행사일처럼 고정된 기한이 있는 경우.
- 여러 단계가 순차 의존하는 구현 과제(개발, 심사, 인증, 납품).
- 이미 지연 중인 프로젝트의 원인 진단과 재계획.

키워드 트리거: 일정, 로드맵, 마일스톤, 마감, 출시, 런칭, 스프린트, 리스크, 지연, 우선순위, 계획, 간트, WBS, 담당, timeline, milestone, dependency.

빼도 된다:

- 단일 부서가 하루 안에 끝내는 조사·문서 요청.
- 순수 학술 질문이나 개념 설명.
- 실행 계획 없이 판단만 필요한 경우(전략팀 결론으로 끝나는 경우).

## 3. 수집해야 할 정보

### 3.1 사용자·저장소에서 (내부)

- [ ] 확정된 마감일과 그 근거(계약, 공모 마감, 시즌, 투자 조건)
- [ ] 기존 백로그, 이슈 목록, 이전 계획 문서
- [ ] 저장소 git log와 최근 커밋 빈도로 실제 진행 속도 추정
- [ ] CI·배포 파이프라인(.github/workflows 등)과 배포 소요 시간
- [ ] AGENTS.md·CONTRIBUTING.md에 정의된 필수 검증 절차(예: npm test, git diff --check)를 릴리스 게이트로 등록
- [ ] 참여 인원, 역할, 주당 가용 시간, 겸업 여부
- [ ] 이미 잡힌 휴가·다른 프로젝트 일정
- [ ] 승인 절차(누가 무엇을 승인해야 다음으로 넘어가는가)

### 3.2 웹·외부 소스에서 (외부)

- [ ] 한국 공휴일·연휴 일정(공공데이터포털 특일 정보, 한국천문연구원). 설·추석 연휴는 2주 가까이 속도를 떨어뜨린다
- [ ] 앱스토어·구글플레이 심사 소요 기간과 반려 시 재제출 주기
- [ ] 인증·심사 리드타임: KC 인증, 전자금융업 등록, ISMS-P, 게임물등급, 식약처 신고 등 해당 분야 절차와 표준 처리 기간
- [ ] 공공 조달 일정(나라장터 공고 기간, 적격심사, 계약 체결 소요)
- [ ] 지원사업·공모전 마감일(K-Startup 공고, 주관기관 일정)
- [ ] 외주·벤더의 표준 리드타임(디자인 외주, 제조 MOQ와 생산 기간, 물류 통관)
- [ ] 성수기·비수기, 업계 행사 일정(전시회, 개학, 연말 프로모션)

리드타임 정보에는 출처와 확인일을 적는다. 심사 기간은 공식 표준 처리 기간과 실제 체감이 다를 수 있으므로 두 값을 함께 적는다.

### 3.3 다른 부서로부터 (입력 의존성)

- [ ] 모든 참여 부서: 작업 항목 목록과 각 항목의 공수 추정(인일 또는 인주)
- [ ] 개발팀: 기술적 선후 관계, 외부 API 연동 대기, 환경 구축 시간
- [ ] 디자인팀: 시안 확정에 필요한 리뷰 라운드 수
- [ ] 전문가팀: 인허가·심사 리드타임과 착수 조건
- [ ] 재무팀: 예산 상한과 자금 집행 가능 시점
- [ ] 영업팀: 고객에게 약속된 일자와 위약 조건
- [ ] 마케팅·광고팀: 사전 홍보 시작 시점(출시일에서 역산)

## 5. 작업 지침

### WBS

- 산출물 기준으로 분해한다. 활동이 아니라 결과물이 노드가 되어야 완료 여부를 판정할 수 있다.
- 리프 작업은 1~5일 크기로 맞춘다. 5일을 넘으면 진행률이 보이지 않고, 반나절 미만이면 관리 비용이 더 크다.
- 작업마다 담당 부서, 산출물 경로, 완료 정의(DoD)를 적는다. DoD 예: "테스트 통과 + 리뷰 승인 + 문서 갱신".
- 번호는 1, 1.1, 1.1.1 방식으로 부여해 의존성 표에서 참조한다.

### 공수 추정

- 3점 추정을 쓴다. 낙관(O), 최빈(M), 비관(P)을 받아 기대값 E = (O + 4M + P) / 6, 표준편차 σ = (P − O) / 6.
- 버퍼는 개별 작업에 붙이지 않고 마일스톤 단위로 모아 둔다. 작업마다 버퍼를 붙이면 버퍼가 그대로 소진된다.
- 실효 가동률은 60~70%로 잡는다. 회의, 리뷰, 문의 대응, 컨텍스트 전환이 나머지를 가져간다.
- 캘린더 일수 = 인일 / (인원 × 실효 가동률)로 환산하고, 공휴일을 뺀 영업일로 날짜를 매긴다.

### 의존성과 크리티컬 패스

- 의존 유형을 표기한다. FS(선행 종료 후 시작), SS(동시 시작), FF(동시 종료), 지연(lag).
- 전진 계산으로 각 작업의 ES(최조 시작)와 EF(최조 종료)를 구한다. EF = ES + 기간.
- 후진 계산으로 LS(최지 시작)와 LF(최지 종료)를 구한다. LS = LF − 기간.
- 총여유 = LS − ES. 총여유가 0인 작업들을 이은 경로가 크리티컬 패스다. 이 경로의 지연은 그대로 최종 일정 지연이다.
- 크리티컬 패스를 문서에 명시하고, 그 위의 작업에는 담당과 상태 확인 주기를 더 촘촘히 잡는다.

### 리스크 레지스터

| 열 | 설명 |
|---|---|
| ID | R-01 형식 |
| 리스크 | "무엇이 발생하면 무엇이 나빠진다" 형태의 문장 |
| 범주 | 기술, 일정, 인력, 규제, 시장, 공급 |
| 확률 | 1~5 |
| 영향 | 1~5 |
| 점수 | 확률 × 영향 |
| 대응 | 회피, 전가, 완화, 수용 중 하나 |
| 조치 | 구체적 행동 |
| 트리거 | 이 신호가 보이면 조치를 발동한다 |
| 담당 | 부서 |
| 기한 | 날짜 |

점수 12 이상은 완화 계획을 반드시 세우고 크리티컬 패스에 조치 작업을 넣는다. 점수 6~11은 트리거만 정의하고 감시한다.

### RACI

작업(또는 마일스톤) × 부서 표를 만든다. R(실행)은 부서 1개, A(최종 책임)도 1개만 둔다. 둘 다 여럿이면 아무도 책임지지 않는다. C(자문)와 I(통보)는 여러 개여도 된다.

### 마크다운 간트

주 단위 표를 기본으로 하고, 필요하면 mermaid를 추가한다.

| 작업 | W1 | W2 | W3 | W4 | W5 |
|---|---|---|---|---|---|
| 1.1 요구 정의 | ## | | | | |
| 1.2 화면 설계 | | ## | ## | | |
| 2.1 구현 | | | ## | ## | |

mermaid를 쓸 경우 gantt 블록에 dateFormat, section, 작업별 시작일과 기간을 적고, 크리티컬 패스 작업에는 crit 태그를 붙인다.

### 진행 추적

- 마일스톤과 크리티컬 패스 작업을 TaskCreate로 등록하고, 상태 변화가 있을 때 TaskUpdate로 갱신한다. TaskList로 미완료 항목을 확인한 뒤 보고서를 쓴다.
- 진행률은 작업 개수가 아니라 완료된 산출물 기준으로 계산한다. "80% 완료"는 신뢰하지 않는다.

### 품질 기준

- 모든 날짜는 절대일(YYYY-MM-DD)과 상대주(W3)를 함께 표기한다. 기준일을 문서 상단에 명시한다.
- 담당 부서가 없는 작업은 계획에 넣지 않는다.
- 크리티컬 패스와 버퍼 위치를 명시한다.
- 외부 리드타임(심사, 배송, 승인)은 우리가 통제할 수 없는 항목으로 따로 표시한다.

### 흔한 실수

- 가동률 100%를 가정한다. 실제로는 60~70%다.
- 리뷰, QA, 수정 반영, 배포 시간을 빼먹는다. 구현 시간만 계산한 일정은 반드시 밀린다.
- 공휴일과 연휴를 무시한다.
- 리스크가 하나도 없는 계획을 낸다. 리스크가 없다는 것은 아직 안 봤다는 뜻이다.
- 순차로만 가능한 작업을 병렬로 배치해 일정을 인위적으로 줄인다.
- 범위 변경을 일정 영향 계산 없이 받는다.

### 윤리·법적 주의

- 근로기준법상 주 52시간 한도를 넘는 초과근무를 전제로 일정을 짜지 않는다.
- 고객·투자자에게 제시할 일정에는 가정과 리스크를 함께 붙인다. 확정 약속으로 보이게 만들지 않는다.
- 일정 압박 때문에 안전, 보안, 법규 검토 단계를 건너뛰는 계획을 만들지 않는다. 그 검토는 크리티컬 패스에 명시적으로 남긴다.
- 위약금이나 계약상 기한이 걸린 일정은 "전문가 확인 필요"로 표시한다.

## 6. 산출물 템플릿

파일 경로: `work/company/<slug>/project-management.md`
선택 표 산출물: `work/company/<slug>/assets/pm-schedule.xlsx` (시트: wbs, dependencies, risks, raci)

헤딩은 3단계로 둔다. 통합 보고서 4절에 그대로 인용해 붙일 때 레벨이 어긋나지 않는다.

```markdown
# PM팀 산출물: <프로젝트명>

### 요약(10줄 이내)
- 기준일과 목표 완료일
- 총 기간과 마일스톤 개수
- 크리티컬 패스 한 줄
- 최상위 리스크 2개와 대응
- 가장 먼저 착수해야 할 작업

### 1. 범위와 제외 범위
- 포함: ...
- 제외: ... (제외를 적어야 범위가 지켜진다)

### 2. WBS
| ID | 작업 | 산출물 | 담당 부서 | 공수(인일, E) | σ |
|---|---|---|---|---|---|

### 3. 마일스톤
| M | 마일스톤 | 검증 조건(게이트) | 목표일 | 상대주 |
|---|---|---|---|---|

### 4. 의존성과 크리티컬 패스
| ID | 선행 | 유형 | ES | EF | LS | LF | 총여유 |
|---|---|---|---|---|---|---|---|
- 크리티컬 패스: 1.1 → 2.1 → 3.2 → M3
- 버퍼 위치와 크기: ...

### 5. 일정표 (주 단위 간트)
| 작업 | W1 | W2 | ... |
|---|---|---|---|

### 6. 리소스 배분
| 부서 | 주당 가용(인일) | 배정(인일) | 과부하 구간 |
|---|---|---|---|

### 7. 리스크 레지스터
| ID | 리스크 | 범주 | 확률 | 영향 | 점수 | 대응 | 조치 | 트리거 | 담당 | 기한 |
|---|---|---|---|---|---|---|---|---|---|---|

### 8. RACI
| 마일스톤 | strategy | product | engineering | ... |
|---|---|---|---|---|

### 미해결 질문·가정
- 가정: 가동률, 인원, 외부 리드타임
- 확인 필요: ... (담당 부서 또는 사용자)
```

## 7. 다른 부서와의 인터페이스

| 부서 | 이 부서가 받는 것 | 이 부서가 주는 것 |
|---|---|---|
| strategy | 목표와 성공 기준, 우선순위 | 목표 달성 가능 일정과 범위 조정 옵션 |
| product | 기능 목록과 우선순위 | 범위별 일정 영향, 컷 라인 제안 |
| engineering | 기술 의존성, 공수 추정, 환경 준비 시간 | 작업 순서, 병목 구간, 릴리스 게이트 |
| design | 시안 리뷰 라운드 수 | 디자인 확정 기한(개발 착수 조건) |
| marketing | 사전 홍보 필요 기간 | 출시일 역산 일정, 콘텐츠 마감일 |
| paid-media | 캠페인 준비 기간 | 집행 시작 가능일 |
| sales | 고객 약속 일자 | 납품 가능 리드타임, 지연 시 통보 시점 |
| finance | 예산 상한, 자금 집행 시점 | 월별 작업량과 지출 발생 시점 |
| support | 운영 인수 준비 항목 | 인수인계 마일스톤과 교육 일정 |
| specialized | 인허가·심사 리드타임 | 심사 착수 기한과 선행 조건 |
