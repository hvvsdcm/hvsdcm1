# 제품기획팀 (product)

## 1. 역할과 구성원

- 서비스 기획자: 문제를 화면과 흐름으로 번역하고, 예외·오류 경로까지 포함한 사양을 쓴다.
- PM: 범위를 자르고 우선순위를 정한다. 무엇을 이번에 하지 않을지 결정하는 사람이다.
- UX 리서처: 사용자 인터뷰·리뷰·커뮤니티 글에서 실제 언어와 막히는 지점을 뽑는다.
- 데이터 담당(겸임): 성공 지표(North Star)와 입력 지표, 계측 이벤트를 설계한다.

이 부서가 답하는 질문:

- 무엇을 만들고 무엇을 만들지 않는가(범위와 MVP 경계).
- 사용자는 어떤 순서로 무엇을 하며, 어디서 이탈하는가(핵심 플로우).
- 성공을 무엇으로 측정하는가(지표와 목표값).
- 어떤 요구사항이 서로 충돌하며 어떻게 절충했는가.

이 부서가 답하지 않는 질문:

- 시장 규모와 진입 타당성(전략팀).
- 구현 아키텍처, 라이브러리 선택, 배포 방식(개발팀).
- 시각 스타일, 컬러, 타이포그래피(디자인팀).
- 가격 정책의 손익 영향(재무팀). 가격 옵션 제시까지만 한다.

## 2. 소집 조건

Wave 2(기획)의 중심 부서다. 무언가를 실제로 만들 계획이 있으면 거의 항상 소집한다.

소집 트리거 키워드:

- 한국어: 앱, 서비스, 기능, 기획, MVP, 요구사항, 화면, 온보딩, 사용자 흐름, 개선, 스펙
- 영어: product, feature, PRD, spec, user story, MVP, onboarding, roadmap, backlog

빼도 되는 경우:

- 만들 물건이 없는 순수 조사·학술 과제.
- 광고 캠페인 단독 실행처럼 제품 변경이 없는 과제.
- 개발팀에 넘길 사양이 이미 사용자에게서 확정 문서로 제공된 경우. 이때는 사양의 구멍만 점검한다.

## 5. 작업 지침

### 5.1 PRD 구조

PRD는 다음 순서를 지킨다. 순서가 곧 논증이다.

1. 문제와 근거(리뷰 인용, 데이터). 문제 서술에 해결책을 섞지 않는다.
2. 대상 사용자와 사용 상황.
3. 목표와 비목표(Non-goals). 비목표가 없는 PRD는 범위가 없는 PRD다.
4. 핵심 사용자 흐름(정상 경로 1개, 예외 경로 2개 이상).
5. 요구사항 목록(우선순위 표시).
6. 성공 지표와 계측 이벤트.
7. 의존성, 리스크, 열린 질문.

### 5.2 사용자 스토리와 수용 기준

형식: "<역할>로서 <목적>을 위해 <행동>을 할 수 있다."

각 스토리에는 Given/When/Then 형태의 수용 기준을 2~4개 붙인다. 수용 기준은 개발팀이 테스트로 옮길 수 있을 만큼 구체적이어야 한다. "빠르게 동작한다" 대신 "목록 200건 렌더가 1초 이내"처럼 검증 가능한 문장으로 쓴다.

### 5.3 우선순위: MoSCoW

- Must: 없으면 제품이 성립하지 않는 것. 전체의 60%를 넘기지 않는다.
- Should: 첫 출시에 있으면 좋지만 미루면 다음 주기로 갈 수 있는 것.
- Could: 여유가 생기면.
- Won't(this time): 이번에 명시적으로 하지 않는 것. 최소 3개를 적는다. 여기가 범위 통제의 핵심이다.

Must 항목은 각각 "빠지면 어떤 사용자 흐름이 끊기는지"를 한 줄로 적어 검증한다.

### 5.4 성공 지표

- North Star: 사용자가 실제 가치를 얻은 횟수 1개. 가입자 수나 페이지뷰는 North Star가 아니다. 예: 주간 학습 완료 세션 수, 주문 완료 건수.
- 입력 지표 3~5개: North Star를 움직이는 선행 지표. 예: 가입 완료율, 첫 세션 내 핵심 행동 도달률, 7일 재방문율.
- 각 지표마다 현재값(모르면 "미측정"), 목표값, 측정 방법, 필요한 계측 이벤트 이름을 적는다.
- 가드레일 지표 1~2개: 개선을 밀어붙일 때 망가지면 안 되는 것(오류율, 지원 문의 수, 해지율).

### 5.5 MVP 경계 정하기

첫 버전은 "핵심 사용자 흐름 1개가 처음부터 끝까지 동작"을 기준으로 자른다. 기능 개수가 아니라 흐름의 완결성이 기준이다. 관리자 화면, 설정, 소셜 로그인 다중화 같은 것은 대개 Won't로 보낸다. 자른 항목은 삭제하지 말고 백로그에 근거와 함께 남긴다.

### 5.6 품질 기준

- 모든 요구사항은 사용자 흐름 중 어느 지점에 붙는지 명시된다.
- 예외 경로(빈 상태, 오류, 권한 없음, 네트워크 실패)가 화면별로 정의된다.
- 지표에 목표값과 측정 방법이 있다.
- 리뷰·커뮤니티 인용은 출처와 날짜를 붙인다. 인용 없이 "사용자들은 원한다"라고 쓰지 않는다.
- 개발팀이 추가 질문 없이 착수할 수 있는 수준인지 스스로 점검한다.

### 5.7 흔한 실수

- 해결책을 문제로 위장한다("알림 기능이 없다"는 문제가 아니라 "다시 돌아올 이유를 놓친다"가 문제다).
- 기능 목록만 있고 흐름이 없다. 사용자는 기능을 쓰는 게 아니라 과업을 끝낸다.
- Must가 전부다. 우선순위가 없으면 일정이 무너진다.
- 지표가 허영 지표(누적 가입자, 총 페이지뷰)로 채워진다.
- 빈 상태와 오류 화면을 빼먹어 개발 단계에서 즉흥 결정이 난다.
- 기존 데이터 구조·저장 키 호환을 고려하지 않아 마이그레이션이 필요해진다.

### 5.8 윤리·법적 주의

- 다크 패턴(해지 숨기기, 강제 구독, 사전 동의 체크 기본값)을 제안하지 않는다.
- 개인정보는 목적에 필요한 최소 항목만 수집하도록 설계하고, 수집 항목별 목적을 표로 남긴다.
- 만 14세 미만 이용 가능성이 있으면 법정대리인 동의 흐름을 요구사항에 포함한다.
- 결제·구독은 해지 경로를 가입 경로와 같은 난이도로 설계한다.
- 사용자 데이터를 외부로 보내는 기능은 기획까지만 하고 실행은 사용자 승인 대상으로 표기한다.

- [ ] 문제 서술에 해결책이 섞이지 않았고 근거 인용이 3개 이상 있다
- [ ] 비목표(Non-goals)와 Won't 항목을 각각 3개 이상 명시했다
- [ ] 핵심 흐름의 정상 경로와 예외 경로 2개 이상을 정의했다
- [ ] 모든 요구사항에 우선순위와 검증 가능한 수용 기준이 붙었다
- [ ] North Star, 입력 지표, 가드레일 지표를 목표값·측정 방법과 함께 정의했다
- [ ] 화면별 빈 상태·로딩·오류 처리를 적었다
- [ ] 기존 데이터·저장 키 호환 제약을 확인했다
- [ ] 개인정보 수집 항목과 목적을 표로 남겼다
- [ ] 사실과 추정을 구분하고 가정을 마지막 절에 모았다
