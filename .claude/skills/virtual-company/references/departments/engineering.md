# 개발팀 (engineering)

## 1. 역할과 구성원

- 프론트엔드: 화면, 상태 관리, 접근성, 브라우저 호환. 정적 사이트 제약에서의 구현을 책임진다.
- 백엔드: API 계약, 인증·세션, 데이터 모델, 마이그레이션.
- AI/데이터: 모델 호출 설계, 프롬프트·평가, 데이터 파이프라인과 비용 추정.
- 모바일: 앱 배포 요건, 웹뷰와 네이티브 경계, 스토어 심사 제약.
- 인프라/DevOps: 배포 파이프라인, 시크릿 관리, 관측(로그·에러), 롤백 전략.

이 부서가 답하는 질문:

- 이걸 이 저장소·이 스택에서 어떻게 만드는가, 얼마나 걸리는가.
- 어떤 기술 결정을 왜 내렸는가(대안과 트레이드오프 포함).
- 어디가 깨질 수 있고 무엇으로 검증하는가(테스트, 롤백).

이 부서가 답하지 않는 질문:

- 무엇을 만들지의 우선순위(제품기획팀).
- 시각 디자인과 브랜드(디자인팀).
- 시장성과 가격(전략팀, 재무팀).

## 2. 소집 조건

Wave 3(제작)의 중심 부서다. 코드가 결과물에 포함되면 소집한다.

소집 트리거 키워드:

- 한국어: 개발, 구현, 코드, 배포, API, 데이터베이스, 버그, 성능, 리팩터링, 프로토타입
- 영어: implement, build, code, deploy, API, schema, migration, refactor, test, worker

빼도 되는 경우:

- 조사·문서만 필요한 과제.
- 코드 없는 목업으로 검증이 끝나는 단계(디자인팀 HTML 목업으로 충분한 경우).
- 외부 노코드 도구로 해결되는 과제. 이때는 기술 검토 의견만 3줄 남기고 빠진다.

## 5. 작업 지침

### 5.1 저장소 규약 준수(이 저장소의 경우)

이 저장소는 빌드 없는 정적 사이트와 Cloudflare Worker API의 조합이다. 다음을 깨지 않는다.

- 브라우저 파일은 번들러 없이 정적 자산으로 동작해야 한다. 빌드 단계를 도입하지 않는다.
- Worker 코드는 Wrangler ES 모듈 런타임과 호환되어야 한다.
- 콘텐츠 데이터와 UI 로직을 분리한다. CSS나 실행 가능한 JS를 HTML로 되돌리지 않는다.
- localStorage 키와 API app 이름은 마이그레이션 없이 바꾸지 않는다.
- D1 스키마 변경은 `worker/migrations/`에 새 번호 파일로 추가한다. 적용된 마이그레이션은 수정하지 않는다.
- 세션 IP·user-agent는 관리자 전용이다. 사용자·공개 경로, 로그, 프런트엔드로 노출하지 않는다.
- 시크릿(`ADMIN_PASSWORD`, 토큰, 로컬 Wrangler 상태)을 커밋하지 않는다.
- 데이터 파일의 건수 불변 조건(예: 단어 2,000개, 문항 98개)을 변경하려면 검증 스크립트와 문서를 같은 변경에 포함한다.

착수 전 `AGENTS.md`와 `docs/ARCHITECTURE.md`를 읽고, 변경 후 다음을 실행한다.

```bash
npm test
git diff --check
```

테스트가 실패하면 고칠 때까지 완료로 보고하지 않는다. 테스트를 약화시켜 통과시키지 않는다.

### 5.2 아키텍처 결정 기록(ADR)

되돌리기 어려운 결정마다 짧은 ADR을 남긴다. 형식은 다음 5줄이면 충분하다.

1. 결정: 무엇을 택했는가.
2. 맥락: 어떤 제약 때문에 이 결정이 필요했는가.
3. 대안: 검토한 다른 선택지 2개와 탈락 이유.
4. 결과: 이 결정으로 생기는 이득과 감수하는 비용.
5. 되돌리는 비용: 나중에 바꾸려면 무엇을 다시 해야 하는가.

라이브러리 추가, 데이터 모델 변경, 인증 방식 변경, 외부 서비스 의존은 ADR 대상이다.

### 5.3 테스트 우선

- 수용 기준을 테스트 이름으로 먼저 옮긴다. 실패하는 테스트를 보고 나서 구현한다.
- 경계값(빈 배열, 0, 최대 길이, 권한 없음, 네트워크 실패)을 최소 1개씩 넣는다.
- 데이터 불변 조건은 검증 스크립트에 넣는다. 사람 눈으로 세는 검증은 무너진다.
- 버그를 고칠 때는 재현 테스트를 먼저 추가한다.
- UI 변경은 기존 E2E 스크립트로 확인하고, 없으면 수동 확인 절차를 보고서에 적는다.

### 5.4 변경 절차

1. 영향 범위를 Grep으로 먼저 파악한다(같은 키·함수명을 쓰는 모든 파일).
2. 작은 단위로 나눈다. 한 변경에 리팩터링과 기능 추가를 섞지 않는다.
3. 데이터 마이그레이션이 필요하면 마이그레이션을 코드보다 먼저 배포하는 순서를 명시한다.
4. 변경 후 전체 diff를 다시 읽는다. 의도하지 않은 포맷 변경, 디버그 코드, 주석 잔여물을 제거한다.
5. 롤백 방법을 한 줄로 적는다.

### 5.5 품질 기준

- 새 코드에 실행 가능한 검증(테스트 또는 검증 스크립트)이 붙는다.
- `innerHTML`에 들어가는 데이터는 이스케이프하고, 단일 값은 `textContent`로 넣는다.
- 새 탭 링크에 `rel="noopener"`를 붙인다.
- API 오류 메시지는 안정적인 JSON으로 반환하고 내부 예외 상세는 서버 로그에만 남긴다.
- 성능은 숫자로 말한다(응답 시간, 번들 크기, 쿼리 수).
- 주석은 문법을 설명하지 않는다. 제약과 이유를 적는다.

### 5.6 흔한 실수

- 사양의 예외 경로를 구현하지 않고 정상 경로만 만든다.
- 빌드가 필요한 라이브러리를 무심코 들여와 정적 배포 모델을 깨뜨린다.
- 마이그레이션 파일을 수정해서 이미 적용된 이력과 어긋나게 만든다.
- 스크립트 로드 순서 의존을 모른 채 파일을 옮긴다.
- 테스트를 나중에 하겠다고 하고 끝낸다.
- 시크릿·토큰을 로그나 응답에 흘린다.
- 추정 시간을 낙관적으로만 적는다. 검증·리뷰·배포 시간을 포함하지 않는다.

### 5.7 윤리·법적 주의

- 사용자 데이터를 외부 서비스로 보내는 코드는 사용자 승인 전까지 비활성 상태로 둔다.
- 개인정보를 로그에 남기지 않는다. 식별자는 해시하거나 마스킹한다.
- 오픈소스 라이선스를 확인하고 GPL 계열을 정적 사이트에 무단 편입하지 않는다.
- 크롤링·스크래핑 코드는 대상 서비스 약관과 robots 정책을 확인하고, 요청 간격을 둔다.
- 광고·추적 스크립트는 동의 없이 기본 활성화하지 않는다.
