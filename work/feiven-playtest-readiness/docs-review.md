검토 중 추가로 확인한 사실 (문서 외)
- r20-playtest 릴리스의 `FEIVEN-Playtest-Setup.exe`는 r20.1과 **바이트 동일** (302,278,948 bytes, sha256 fc4b5f18…bf01). 즉 R20과 R20.1은 같은 설치파일이며, R20.1은 안내문·`release-info.json`·`PLAYTEST-GUIDE.ko.txt`를 추가한 재발행이다.
- r19-playtest 릴리스는 여전히 공개 상태(prerelease 아님, draft 아님)이고 356,705,306 bytes짜리 다른 설치파일(sha256 bf6586cc…)을 그대로 내려받을 수 있다.
- 세 태그(r19, r20, r20.1) 모두 같은 커밋 de70889(Initial commit)를 가리킨다. GitHub의 `releases/latest`는 릴리스 `created_at`(=태그 커밋 시각) 기준 최신 non-prerelease를 고르므로 셋이 동점이다. 현재는 r20.1로 해석되고 있으나(API `get_latest_release` 확인) 순서가 보장되는 구조가 아니다.
- 설치파일은 Inno Setup 6.7.0으로 innoextract 1.9/1.10-dev 모두 헤더를 읽지 못해(“Unexpected setup loader revision: 2”) 설치 후 용량·MinVersion·UAC 여부는 문서에서 확인할 수 없었다. 해당 항목은 제안 README에 플레이스홀더로 남겼다.

심각도 기준

- **nice**: 여유가 있으면

## A. blocker

### 1. R19 설치파일이 아직 공개 상태로 내려받기 가능 (blocker)
- 증거: GitHub 릴리스 r19-playtest — `prerelease:false`, 자산 `FEIVEN-Playtest-Setup.exe` 356,705,306 bytes, `download_count:0`이지만 링크 활성. 릴리스 본문 r20.1: “**R19 등 예전 설치파일 대신 이 버전을 사용해 주세요.**”, 가이드: “R19는 현재 서버용 배포본이 아닙니다.”
- 문제: 디시 독자가 `/releases` 목록으로 들어오면 세 개의 같은 이름(FEIVEN-Playtest-Setup.exe) 파일이 보인다. R19를 받으면 서버 접속이 안 되고, 이슈/댓글이 “접속 안 됨”으로 쏟아진다. 문서로 “쓰지 마세요”라고 하는 것보다 받을 수 없게 하는 것이 낫다.
- 수정:
  1. r19-playtest 릴리스의 exe 자산을 삭제하거나, 최소한 릴리스를 **Pre-release로 전환**하고 본문 맨 위에 `> **사용 중지된 버전입니다. 현재 서버와 호환되지 않습니다. r20.1-playtest를 받으세요.**`를 추가.
  2. r20-playtest도 같은 조치(아래 2번).

### 2. r20과 r20.1이 동일 파일인데 두 릴리스가 나란히 공개, README는 “R20” (blocker, 1번과 묶어 처리)
- 증거: r20 자산 digest `sha256:fc4b5f18…bf01` = r20.1 자산 digest. README.md: “- FEIVEN R20 Playtest”, 릴리스 이름 “FEIVEN R20.1 Playtest”, release-info.json `"release": "R20.1 Playtest"`, 가이드 1행 “FEIVEN R20.1 플레이테스트”.
- 문제: 독자 입장에서 “R20이랑 R20.1 뭐가 달라요? 다시 받아야 해요?”가 반드시 나온다. 300MB 재다운로드를 유발한다. 또한 r20 릴리스 본문의 해시는 대문자(`FC4B…`)이고 r20.1은 소문자라 “해시가 다르다”는 오해가 생긴다.
- 수정:
  1. r20-playtest 릴리스를 Pre-release로 전환하고 본문 위에 `> r20.1-playtest와 같은 설치파일입니다. 이미 R20을 설치했다면 다시 받을 필요가 없습니다. 안내는 r20.1을 보세요.` 추가. 자산은 남겨도 무방(해시 동일).
  2. README를 R20.1 기준으로 갱신하고 “R20 설치본 = R20.1 설치본, 재설치 불필요” 한 줄을 명시 (제안 README 반영).
  3. 앞으로는 게임 빌드가 그대로인 재발행은 새 태그를 만들지 말고 기존 릴리스 본문/자산만 갱신할 것.

### 3. 수집 정보·개인정보 안내가 어디에도 없음 (blocker)
- 증거: 네 문서 모두 “비밀번호·개인정보를 첨부하지 마세요”만 있고, 게임이 무엇을 수집하는지(계정 이메일/Google 계정 식별자, 접속 IP, 전적·경험치, 크래시·계측 로그 여부)와 삭제 요청 창구가 없다. 릴리스 본문은 “자동 대전 검증에는 검증용 계측이 포함되며”라고 하여 계측(telemetry) 존재를 암시한다.
- 문제: Google 로그인과 회원가입을 받는 순간 개인정보 처리 안내(수집 항목·목적·보유기간·문의처)가 필요하다. 디시 유저는 “뭐 수집함?”을 가장 먼저 묻고, 답이 없으면 “정보 수집 툴”로 낙인 찍힌다. 계정 삭제 방법이 없으면 이슈로 온다.
- 수정: README에 `## 수집하는 정보와 개인정보` 절 추가. 항목은 운영자만 알 수 있으므로 제안 README에 `<<운영자 기입>>` 플레이스홀더. 최소 포함: 수집 항목, 용도(매칭·전적·부정행위/오류 확인), 보유 기간(테스트 종료 후 삭제 여부), 삭제·문의 연락처(이메일 1개), 제3자 제공 없음 여부.

### 4. 테스트 일정·운영 시간대가 없음 (blocker, 용량 18명 기준)
- 증거: 네 문서 어디에도 날짜·시간·서버 지역이 없다. 릴리스 본문: “총 18명이 동시에 플레이… 대기열은 최대 48명”.
- 문제: 디시 글 하나가 수백 명을 동시에 부른다. 동시 18명 + 대기 48명 = 66명 이후는 전부 실패 경험만 하고 나간다. 시간대를 나눠 공지하지 않으면 첫날 평판이 “서버 터짐”으로 굳는다.
- 수정: README/디시 글에 `## 테스트 일정` 절(플레이스홀더). 권장 운영 방식: (a) 공개 시간을 하루 2–3개 슬롯(예: 20:00–22:00 KST)으로 쪼개 공지, (b) 슬롯 밖에는 로컬 훈련만 안내, (c) 서버 지역(예: 한국/일본 리전) 명시 → 핑 문의 감소. 값은 운영자 기입.

### 5. `releases/latest` 의존이 취약함 — 링크 정책 통일 (should-fix)
- 증거: README.md “다운로드: https://github.com/hsdc1258/feiven-playtest/releases/latest”, 가이드 “https://github.com/hsdc1258/feiven-playtest/releases/latest”, 릴리스 본문은 exe 직링크(`/releases/download/r20.1-playtest/...`). 세 태그의 커밋이 동일(de70889)해 `latest` 선정 기준(`created_at`)이 동점.
- 문제: 지금은 우연히 r20.1이 latest이지만, 같은 커밋에 태그를 하나 더 붙이면 어느 쪽이 latest가 될지 보장이 없다. 또 README와 가이드는 “latest”, 릴리스는 “pinned”라 링크가 세 종류다.
- 수정 (권장 정책):
  1. 디시 글과 README는 **릴리스 페이지(태그 고정)** `https://github.com/hsdc1258/feiven-playtest/releases/tag/r20.1-playtest`를 1차 링크로. 이유: 해시·안내·SmartScreen 절차가 같은 화면에 있고, 모바일(디시 앱)에서 클릭해도 300MB exe가 폰으로 떨어지지 않으며, 파일명이 세 릴리스 모두 같아 “어느 릴리스 파일인지”가 페이지로 식별된다.
  2. exe 직링크는 릴리스 본문 안에서만 두 번째 링크로 유지(“PC에서 바로 받기”).
  3. 앞으로 릴리스마다 README 갱신 커밋에 태그를 붙여 `created_at`이 단조 증가하게 한다(지금은 README 갱신 커밋 c983b3e에 태그가 없다).
  4. GitHub 릴리스 자산 대역폭 자체는 수백 명 규모에서 문제 없음. 링크 형태만 통일하면 된다.

### 6. 해시 표기 대소문자 불일치 + 확인 방법 부재 (should-fix)
- 증거: README.md `FC4B5F18…BF01`(대문자); release-body / SHA256SUMS.txt / release-info.json 소문자; r20 릴리스 본문 대문자. README “`SHA256SUMS.txt`로 무결성을 확인할 수 있습니다” — 방법 없음.
- 문제: `certutil`은 소문자, PowerShell `Get-FileHash`는 대문자로 출력한다. 대소문자 차이를 “해시 불일치”로 오해하는 제보가 나온다. 확인 명령이 없으면 아무도 확인하지 않는다.
- 수정: 전부 소문자로 통일하고 “대소문자는 구분하지 않습니다” 한 줄 추가. 명령 2개 제시: `certutil -hashfile "%USERPROFILE%\Downloads\FEIVEN-Playtest-Setup.exe" SHA256` / `Get-FileHash ... -Algorithm SHA256`. (제안 README 반영)

### 8. 대기열 가득 참 상황의 메시지·재시도 예절이 문서마다 다르고 불완전 (should-fix)
